DEMO: WHEN THE SAFETY CHECK IS TOO SLOW, WHO DECIDES WHAT THE GATE DOES?
Synthetic data only. Portkey OSS gateway, local mock upstream, local webhook.
==============================================================================

ACT 1 — THE GAP. Destructive action; the safety webhook is degraded.
Straight to the gateway, nothing says what to do on timeout.
------------------------------------------------------------------------------
  HTTP 200 in 1.04s -> REQUEST EXECUTED
  webhook result: Request timed out after 1000ms
  fail_on_error=False  deny=False
  upstream said: [MOCK LLM] Executed request: delete all records for customer 4417
  => The check TIMED OUT and the delete went through anyway. Fail-open by default.

ACT 2 — THE PRIMITIVE THAT EXISTS. Same timeout, failOnError: true.
The docs ship this toggle. It works — if a human flips it correctly,
by hand, for every action, forever.
------------------------------------------------------------------------------
  HTTP 446 in 1.01s -> REQUEST BLOCKED
  webhook result: Request timed out after 1000ms
  fail_on_error=True  deny=True
  => Same timeout, opposite outcome. The primitive exists; the POLICY doesn't.

ACT 3 — THE PROPOSAL. Failure mode DERIVED from (risk tier,
verification), attached SERVER-SIDE by the policy proxy. The action
is parsed from the payload's tool_call — callers can't label
themselves. Only VERIFIED labels earn fail-open. Webhook degraded.
------------------------------------------------------------------------------

  caller -> payload tool_call=analytics-server/run_report
  proxy derived: action=analytics-server/run_report  tier=1
  HTTP 200 in 1.03s -> REQUEST EXECUTED
  webhook result: Request timed out after 1000ms
  fail_on_error=False  deny=False
  upstream said: [MOCK LLM] Executed request: run the weekly usage report

  caller -> payload tool_call=comms-server/post_slack_message
  proxy derived: action=comms-server/post_slack_message  tier=2
  HTTP 200 in 0.03s -> REQUEST EXECUTED
  guardrail ran ASYNC — the request never waited on the degraded
  check; the audit receipt lands out of band (shown below).

  caller -> payload tool_call=crm-server/delete_customer
  proxy derived: action=crm-server/delete_customer  tier=3
  HTTP 446 in 1.02s -> REQUEST BLOCKED
  webhook result: Request timed out after 1000ms
  fail_on_error=True  deny=True

ACT 4 — THE HOSTILE CALLER, TWO WAYS.
4a) Label spoofing: the payload is a delete, but the caller labels
    it a read-only report, hoping for tier-1 fail-open. The proxy
    derives the action from the payload and logs the mismatch.
------------------------------------------------------------------------------
  caller -> header says run_report; payload tool_call=crm-server/delete_customer
  proxy derived: action=crm-server/delete_customer  tier=3 (mismatch logged)
  HTTP 446 in 1.02s -> REQUEST BLOCKED
  webhook result: Request timed out after 1000ms
  fail_on_error=True  deny=True
  => The label is attacker-controlled; the payload is not. Enforcement
     follows the payload.

4b) Config injection: same delete, caller attaches its OWN fail-open
    guardrail config. The proxy strips it and enforces the tier.
------------------------------------------------------------------------------
  caller -> delete payload + its own fail-open config
  proxy derived: action=crm-server/delete_customer  tier=3 (client config stripped)
  HTTP 446 in 1.01s -> REQUEST BLOCKED
  webhook result: Request timed out after 1000ms
  fail_on_error=True  deny=True
  => The caller cannot choose its own risk tier OR its own policy.
     That is enforcement.
